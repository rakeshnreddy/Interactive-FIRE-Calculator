## R2 — P1: idempotency is not atomic

`functions/_lib/planReviews.ts:94–166` selects then separately inserts. `migrations/0007_monthly_plan_reviews.sql:25` is a non-unique index. Concurrent requests can both see no row and insert duplicates. The existing-record path also ignores changed decision/notes/deferDays and returns an earlier choice as a successful replay. Define exact replay versus changed-intent behavior; implement a database-enforced unique operation/cycle key and atomic conflict handling. Do not modify already-applied0007 in place. Test concurrent duplicates, exact replay, changed-intent conflict and next legitimate cycle.

## R3 — P1: client evidence date determines due date

`src/lib/planReviews.ts:186–188` validates only date shape; impossible dates normalize, e.g.2026-02-30. `functions/_lib/planReviews.ts:129–137` computes next due/defer date from client evidenceDate rather than trusted completion/deferral time. An eligible plan with evidence2099-01-01 can suppress reminders until2099; old evidence can make a just-completed review immediately overdue. Reject impossible/future evidence dates; separate evidence age from server-recorded review timing and schedule from trusted action time. Test UTC boundaries, >=7-day eligibility, stale evidence, impossible dates and future manipulation.

## R4 — P1: navigation guard and exact-version path incomplete

`src/PlanningWorkspace.tsx:455–487` protects internal load buttons, but `src/App.tsx:7283` navigateTo pushes history and replaces active plan state directly without consulting workspace dirty state. Leaving and returning via top navigation can lose draft metadata or replace inputs without confirmation. The parser `src/lib/navigation.ts` also converts invalid explicit versions to null; downstream startup then treats that as an omitted version and loads latest. Invalid explicit version must be a controlled error, never a silently substituted decision. Route dirty decisions through a shared guard (including back/forward as appropriate). Prove actual edit→navigation→cancel preservation and edit→confirm→exact-version load in the real app, not only isolated SSR tests.

## R5 — P1: dashboard ignores completed/deferred reviews

`src/App.tsx:3216–3220` reads `(plan as any).dueStatus`, otherwise calculates from plan creation/update alone. Actual saved plans are loaded by loadAccountPlans/setSavedPlans (5661), and no app call consumes `/api/plans/due-reviews`. Neither the existing plan-list API nor SavedPlan supplies persisted dueStatus. Completing/deferring a review updates workspace-local state only; dashboard can continue showing the old due card. Connect typed persisted review state, refresh after review and on reload, and verify due→completed/deferred transitions without mutating plan dates. The harness creates another aged plan to show a card, which cannot prove completed/deferred cards update correctly.

## R6 — P2: evidence freshness is overstated

`src/PlanningWorkspace.tsx:312–318` submits today as evidenceDate automatically, regardless of which dated balances/assumptions the user reviewed. `src/App.tsx:4279` uses goal.updatedAt as balance evidence date; renaming/updating goal metadata can relabel old financial evidence as fresh. Use actual evidence/source dates or accurately label metadata-update dates. Do not claim latest balance/transaction evidence without provenance. Test stale source plus metadata edit and review confirmation; source age must not reset silently.
