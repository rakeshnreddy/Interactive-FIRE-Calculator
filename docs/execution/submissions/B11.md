## Problem and change

User problem:
Users lacked a persistent monthly review model to track plan progress over time against current financial balances and evidence. The existing application offered only static guidance (`buildCalculatorFollowUp`) without recording review milestones, choices (keep, revise, defer), or next review due dates. Furthermore, there was no enforcement of the minimum 7-day maturation period following plan baseline creation, nor was review data integrated into account exports and privacy erasures.

Implementation:
1. **Additive Schema Migration**:
   - Authored and applied migration `0007_monthly_plan_reviews.sql` and `0008_plan_reviews_idempotency.sql` adding `plan_reviews` to Cloudflare D1 with database-enforced unique idempotency index.
   - Schema tracks: `id`, `user_id`, `plan_id`, `plan_version_number`, `evidence_date`, `decision` ('keep', 'revise', 'defer'), `status` ('draft', 'completed', 'deferred'), `notes`, `completed_at`, `deferred_until`, `next_review_due`, `idempotency_key`, `payload_hash`, `created_at`, `updated_at`.
2. **Enforced >= 7-Day Returning Review Rule**:
   - In `functions/_lib/planReviews.ts` and `functions/api/plans/[id]/reviews/index.ts`, enforced that the first returning review must occur at least 7 days after the plan's initial creation baseline.
   - Submissions made prior to the 7-day threshold are rejected with HTTP 400 and structured error `{ code: 'TOO_EARLY_REVIEW', error: 'First review must be at least 7 days after plan baseline' }`.
3. **Review Decision Lifecycle**:
   - "Keep": Records confirmation of current plan trajectory with status `completed` and calculates next due date ~30 days out from server action time.
   - "Revise": Routes user to the planning workspace with inputs pre-populated, enabling Version revision.
   - "Defer": Records status `deferred` with an updated due date (7-14 days out from server action time) without altering plan parameters.
4. **Due Reviews Endpoint**:
   - Implemented `GET /api/plans/due-reviews` returning upcoming and overdue review cards for the authenticated user, complete with plan name, current version, and due date.
5. **Account Export & Erasure Hooks**:
   - Updated `functions/api/account-data/export.ts` to include `planReviews` in the exported JSON payload.
   - Updated `functions/api/account-data/index.ts` DELETE handler to purge `plan_reviews` records on account deletion.
6. **Idempotency & Cross-Tenant Security**:
   - Prevented duplicate active reviews for the same version and cycle using database unique index and SHA-256 payload hash (exact replay returns 200 `isDuplicate: true`; conflicting repeat returns 409 `IDEMPOTENCY_CONFLICT`).
   - Enforced tenant boundary checks: Tenant B cannot review Tenant A's plan (`/api/plans/:id/reviews` returns HTTP 404).
