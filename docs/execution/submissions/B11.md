## Problem and change

User problem:
Users lacked a persistent monthly review model to track plan progress over time against current financial balances and evidence. The existing application offered only static guidance (`buildCalculatorFollowUp`) without recording review milestones, choices (keep, revise, defer), or next review due dates. Furthermore, there was no enforcement of the minimum 7-day maturation period following plan baseline creation, nor was review data integrated into account exports and privacy erasures.

In the 2026-09-25 review, Astra identified that the previous C09 proof posted `decision: revise` directly without selecting the UI radio/button, presenting an explicit edit/save next step, saving Version 3, or verifying that older versions remain immutable.

Implementation:
1. **Additive Schema Migration**:
   - Authored and applied migration `0007_monthly_plan_reviews.sql` and `0008_plan_reviews_idempotency.sql` adding `plan_reviews` to Cloudflare D1 with database-enforced unique idempotency index.
   - Schema tracks: `id`, `user_id`, `plan_id`, `plan_version_number`, `evidence_date`, `decision` ('keep', 'revise', 'defer'), `status` ('draft', 'completed', 'deferred'), `notes`, `completed_at`, `deferred_until`, `next_review_due`, `idempotency_key`, `payload_hash`, `created_at`, `updated_at`.
2. **Enforced >= 7-Day Returning Review Rule**:
   - In `functions/_lib/planReviews.ts` and `functions/api/plans/[id]/reviews/index.ts`, enforced that the first returning review must occur at least 7 days after the plan's initial creation baseline.
   - Submissions made prior to the 7-day threshold are rejected with HTTP 400 and structured error `{ code: 'TOO_EARLY_REVIEW', error: 'First review must be at least 7 days after plan baseline' }`.
3. **Review Decision Lifecycle & Revise UI Journey**:
   - "Keep": Records confirmation of current plan trajectory with status `completed` and calculates next due date ~30 days out from server action time.
   - "Revise": Selecting "Revise assumptions" in UI submits the review and displays an explicit `<aside className="plan-revision-prompt" data-testid="plan-revision-prompt">` next-step banner directing the user to the FIRE calculator to adjust financial assumptions (spending, savings rate, retirement age). The metadata form remains clearly scoped for version notes and label. In `App.tsx`, added `<aside className="plan-context-bar">` displaying the loaded plan context on `/calculators/fire` with a direct "Back to Planning Workspace" route.
   - "Defer": Records status `deferred` with an updated due date (7-14 days out from server action time) without altering plan parameters.
4. **Due Reviews Endpoint**:
   - Implemented `GET /api/plans/due-reviews` returning upcoming and overdue review cards for the authenticated user, complete with plan name, current version, and due date.
5. **Account Export & Erasure Hooks**:
   - Updated `functions/api/account-data/export.ts` to include `planReviews` in the exported JSON payload.
   - Updated `functions/api/account-data/index.ts` DELETE handler to purge `plan_reviews` records on account deletion.
6. **Idempotency & Cross-Tenant Security**:
   - The UI review sends no explicit key, so the server derives `v2:<evidenceDate>`. Replay is tested using the persisted review's exact key (`persistedReviseReview.idempotency_key`), date, decision, and notes, verifying HTTP 200 replay with `isDuplicate: true` and 1 row in D1. Conflicting intent with the same key returns HTTP 409 with structured code `IDEMPOTENCY_CONFLICT`; D1 is queried after the conflict to confirm exactly 1 row persists with the original `revise` intent and key, and total plan reviews remain strictly 3 (defer, keep, revise).
   - Enforced tenant boundary checks: Tenant B cannot review Tenant A's plan (`/api/plans/:id/reviews` returns HTTP 404).
7. **Comprehensive Automated Proof Harness & Negative Tests**:
   - Updated Stage 4 of `docs/execution/evidence/C09/run_c09_proofs.mjs` to execute the full user journey: generate truthful synthetic seeds for Version 1 and Version 2 via `calculateFirePlan(snapshot.plan)` with full finite `requiredPortfolio`, select revise radio in UI (`input[value="revise"].isChecked()`), submit revision review, verify explicit next-step banner, navigate to FIRE calculator via "Open calculator", assert loaded v2 value is `50000` on `input#fire-annual-expense`, fill `45000`, assert edited value before saving Version 3, return to Planning Workspace, save Version 3, verify Version 3 persistence and calculation diff in D1 by parsing raw D1 schema `fire_plan_inputs.input_json` and `fire_plan_results.result_json` (requiring finite numbers, changed requiredPortfolio, and exactly 1 row for Version 3 version/input/result), verify byte-identical immutability of Versions 1 & 2 across ALL THREE tables (`plan_versions`, `fire_plan_inputs`, **and** `fire_plan_results`, requiring 1 row in all 12 table sets), reload Version 3 deep link, navigate to calculator to verify `input#fire-annual-expense` displays 45000 and cross-check against D1 snapshot, and verify replay and conflict behavior.
   - Enforced strict runtime deployment inputs validation (`C09_CANDIDATE_SHA`, `C09_DEPLOYMENT_ID`, `C09_PREVIEW_URL`) without stale defaults, requiring preview D1 UUID `0dbad68e-7493-452f-8504-98d4c61ee5da` and preview environment.
   - Added collector-level unit and negative tests in `docs/execution/evidence/C09/run_c09_proofs.test.mjs` (55 total tests passing) testing truthful `calculateFirePlan` seeds, fake result shape rejection without `requiredPortfolio`, real 3-review history sequence (defer, keep, revise), missing `postConflictReview` rejection, total count increase rejection (3 -> 4), deployment inputs validation, deployment metadata verification, unchecked radio, raw D1 rows, malformed JSON, non-finite values, unchanged financial assumptions, unchanged calculation results, missing immutability rows, mismatched replay keys, absent `isDuplicate` flags, wrong conflict codes, duplicate rows after conflict, and fixture server security defenses.
