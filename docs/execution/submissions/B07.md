## Problem and change

Task B07 establishes the honest deletion, export, and disaster recovery contract for FinPath95. Previously, account deletion cleared child tables in D1 but left the user record completely removed without a tombstone. As a result:
1. In-flight, delayed, or offline-queued API writes could arrive after deletion and recreate the user record or insert orphan rows.
2. Restoring a pre-disaster D1 database backup from historical snapshots would silently resurrect deleted user accounts and data.
3. Export did not enforce a fail-closed guarantee on deleted users.
4. Client-side financial form drafts in `localStorage` were not explicitly purged on account deletion.
5. The boundary between D1 database erasure and external Clerk identity was not clearly documented.

Implemented changes:
1. **Durable Tombstone Architecture (`functions/_lib/accountData.ts`, `functions/_lib/persistence.ts`)**:
   - `deleteAccountData()` executes hard deletion across all 14 child tables and installs a durable tombstone in `users`:
     ```sql
     UPDATE users SET deleted_at = ?, updated_at = ? WHERE id = ?
     ```
   - Added `UserDeletedError` mapped by `handleApiError` to **HTTP 410 Gone** (`ACCOUNT_DELETED`).
   - Every API endpoint checks `assertUserNotDeleted()` prior to reading or writing data.
2. **Offline Replay / UPSERT Conflict Guard (`persistence.ts`)**:
   - `readOrCreateUser` uses:
     ```sql
     INSERT INTO users (id, email, name, created_at, updated_at) VALUES (...)
     ON CONFLICT(id) DO UPDATE SET email = excluded.email, name = excluded.name, updated_at = excluded.updated_at
     WHERE users.deleted_at IS NULL
     ```
   - Prevents delayed profile syncs or auth handshakes from clearing tombstones or resurrecting deleted users.
3. **Disaster Recovery Tombstone Replay Protocol (`replayTombstones`)**:
   - Implemented `replayTombstones(database, tombstones)` in `functions/_lib/accountData.ts`.
   - Idempotently re-purges child tables and re-applies `deleted_at` tombstones on restored backup snapshots before serving live traffic.
4. **Client-Side Draft Clearing Protocol (`clearLocalDrafts()`)**:
   - Implemented in `src/App.tsx` and triggered on account deletion confirmation.
   - Explicitly purges all keys matching `finpath.*`, `firecalc.*`, and `fire_calc_*` from `localStorage`.
   - Explicitly preserves `finpath.colorMode` (theme preference) and non-app keys on shared devices.
5. **Truthful Erasure Boundary Documentation (`docs/DATA_DELETION_AND_RECOVERY.md`)**:
   - Documents boundaries across D1 relational store, Clerk IDP, browser storage, and Cloudflare automated backups.
   - Establishes DR operator runbook for database restores.
   - Isolates statutory retention decisions from unreviewed background archiving.
6. **Comprehensive Test Suite (`src/deletionAndRecovery.test.ts`)**:
   - 8 comprehensive tests validating two-user isolation, tombstone durability, delayed write fail-closed (410), UPSERT replay guards, deletion idempotency, export snapshot consistency, DR backup restore drill with tombstone replay, and scoped draft clearing.
