## Problem and change

Task B04 establishes atomic, retry-safe calculator result saving and downstream entity creation. Previously, downstream draft creation (e.g. `createGoal`, `createAccount`, `createPlanDraft`) was executed in separate database queries prior to inserting `saved_calculator_results`. If a network interruption or database failure occurred mid-flight, orphan goals or accounts remained in the database. Furthermore, retry requests could generate duplicate records, conflicting payloads with identical keys were not guarded against, header/body idempotency keys lacked unified normalization, and metric array reordering created conflicting destination targets under equal hashes.

Implemented changes:
1. **Additive Schema Migration (`migrations/0005_saved_calculator_idempotency.sql`)**:
   - Added `idempotency_key TEXT` and `payload_hash TEXT` columns to `saved_calculator_results`.
   - Created partial unique index `idx_saved_calculator_results_user_idempotency` on `(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL` scoped strictly to `user_id`.
2. **Deterministic Destination-Aligned Payload Hashing (`hashCalculatorPayload`) (R2)**:
   - Preserves semantically meaningful array order of `result.metrics` and `result.assumptions` while deterministically sorting object keys in `inputValues`.
   - Inverted C02 review reproduction into a permanent regression test: reordering destination-affecting metrics generates unequal hashes, differing destination targets ($100 vs $200), and triggers HTTP 409 `IDEMPOTENCY_CONFLICT` on key reuse.
   - Computes SHA-256 digest using standard Web Crypto API (`crypto.subtle.digest`).
3. **Atomic Single-Batch Destination + Result Persistence (`createSavedCalculatorResult`)**:
   - Bundles destination insert statements (`goals`, `financial_accounts`, `account_balances`, or `plans`) and `saved_calculator_results` insert into a single `database.batch(...)` transaction.
   - Any failure or abort rolls back the entire batch, eliminating orphan entities completely.
4. **Idempotent Retry Resolution (`CALCULATOR_SAVE_STATUS`)**:
   - Checks for existing `(user_id, idempotency_key)` before and upon catching unique constraint races.
   - If payload hash matches: reads existing entity and returns `{ createdEntity, savedResult, saveStatus: 'retry' }` with HTTP 200.
   - If payload hash differs: throws `IdempotencyConflictError` and returns HTTP 409 with `{ code: 'IDEMPOTENCY_CONFLICT' }`.
5. **Unified Header and Body Idempotency Key Normalization (`resolveIdempotencyKey`) (R3)**:
   - Validates header and body keys with identical type (string) and length (1–120 characters) constraints before database interaction.
   - Rejects key disagreement with typed 400 error `{ code: 'IDEMPOTENCY_KEY_MISMATCH' }`.
   - Validated across all 10 cells of the Key Input Table, guaranteeing zero database writes on rejection.
6. **Client Idempotency Ownership & Coordination (`CalculatorSaveCoordinator`) (R1)**:
   - Implemented `CalculatorSaveCoordinator` in `src/lib/calculatorSaveManager.ts` and wired into `src/App.tsx`.
   - Owns the idempotency key and snapshot at the logical save boundary; retries after lost responses or network failures reuse the exact same key and snapshot.
   - Deduplicates parallel in-flight clicks; clears pending state on confirmed completion or user account switch; avoids hash-only keys.
7. **Multi-Tenant Isolation**:
   - Unique constraints and lookups are strictly scoped to `user_id`. Foreign users utilizing identical idempotency keys create independent records without collision or data leakage.
8. **Transaction Destination Guard**:
   - Saving to `conversionRoute: '/transactions'` creates `saved_calculator_results` with `created_entity_type: null` and creates zero fake rows in `transactions`.
9. **Real SQLite D1 Integration Test Suite (`src/calculatorResults.test.ts`)**:
   - Implemented in-memory SQLite D1 harness using Node's `DatabaseSync` running migrations 0001 through 0005.
   - Validated atomicity rollback on injected failure (zero orphans), identical retry resolution, 409 conflict, multi-tenant isolation, concurrency race handling, key input normalization, and transaction destination integrity.
