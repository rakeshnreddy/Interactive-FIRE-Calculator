# C20 dated-return migration decision — 2026-09-30

Keep the old periodic monthly-return engine and goldens. Add an explicit dated mode using signed amounts and Gregorian ISO dates, UTC calendar-day differences divided by 365 (Microsoft XIRR definition: https://support.microsoft.com/en-us/excel/functions/xirr-function, checked 2026-09-30). Restrict v1 to negative investment flows followed by positive proceeds after sorting and same-day aggregation; more sign changes are unsupported, not guessed. Search log(1+r) between log(0.0001) and log(1001), at most 200 bisections; require relative discounted-flow residual <= 1e-10. Bounded 2–50 flows, amount magnitude <= 1e12, dates 1900–2100, span <=100 calendar years. No zero fallback.

Store a validated optional inputModel in the existing input_json envelope only for dated rows: {values, inputModel}. Legacy numeric maps and their hashes remain unchanged; optional inputModel and modelVersion participate in new canonical hashes. Client/list/export/restore keep actual dates. Old monthly rows remain monthly and acquire no inferred dates. New dated snapshots route to plan drafts, never a currency goal derived from a percentage. No D1 schema change or backfill. Rollback retains envelope/version read support. No financial dates/amounts in analytics or URLs; CSV only on explicit action.

Periodic table correction: the existing solver emits an effective annual return. Convert it back with expm1(log1p(r)/12), not r/12; use the actual rounded monthly horizon, including partial years, and never force the final balance to the entered value. Independently derived zero-contribution +10% and −10% yearly paths verify intermediate balances. A total-loss boundary or a clamped solver result without a reconciling path produces no implied table. The old monthly headline solver and normal golden values are unchanged; old snapshots are not rewritten.
