# B52 — Calculator spacing and explicit result navigation

Checkpoint C17 · P1 · dependency B46. Added by owner 2026-09-30 while the direct Astra pass is active. Owner asked for reasonable density, clear inputs/results without crowding, and buttons that reveal results when those results are not currently displayed.

## User problem and design decision

Inspect actual 1440/390/320 layouts first. Use proximity: the label/help belong closer to their input than the next field; meaningful groups get more space. Keep controls >=44px, editable text >=16px, supporting copy readable, units/basis/errors visible and financial cards opaque. Reduce oversized secondary numbers and unnecessary header stacking before shrinking controls or hiding critical assumptions. Do not add another density switch or another tracker.

References checked 2026-09-30: [NN/G form grouping](https://www.nngroup.com/articles/form-design-white-space/) and [proximity](https://www.nngroup.com/articles/gestalt-proximity/); [GOV.UK details guidance](https://design-system.service.gov.uk/components/details/). These support grouping/progressive disclosure; they do not prove a particular pixel count increases conversion.

## Implement

Use scoped canonical spacing for calculator input/result panels, headers, related fields, secondary metric cards and the primary amount. Preserve all values, calculation contracts, defaults, input labels and helper/error connections.

After an explicit successful FIRE Calculate/Recalculate, generic scenario choice or dedicated scenario choice, reveal the primary answer if outside the usable viewport. Auto-update calculators get one clearly labeled View result button, disabled when input is invalid. Use one shared post-render reveal helper/hook so newly mounted/updated results are targeted, sticky navigation is cleared, and keyboard focus follows the revealed result. If the primary answer is already visible, preserve focus and scroll. Typing, loading the page, disclosure/customization, share/export and save/account actions must not jump to results. Respect reduced motion; use a deterministic immediate reveal without animation. No simulated scrolling or viewport scaling proof.

Likely files: new shared result-reveal helper/hook and tests; App.tsx FIRE action; CalculatorLibrary; CompoundInterestCalculator; SavingsGoalCalculator; CashflowPlanningCalculator; scoped vivid-theme CSS; UI integration tests. No engine, auth, D1, formula, route or dependency change.

## Acceptance and tests

- Success-only reveal targets the committed result, including the initially absent FIRE result.
- Visible answer => no scroll/focus change; offscreen answer => heading/primary amount visible below topbar, keyboard focus on the real result region.
- Invalid inputs => no result action; typing preserves position and editing focus. Saved snapshots/math unchanged.
- Desktop side-by-side and mobile single-column remain clear; minimum touch/input sizes retained. No text overlap, result clipping, document overflow or hidden units at 320/390/1440 in light/dark; actual before/after measurements and screenshots.
- Test the viewport predicate, missing target, result mounted after Calculate, scenario result action, invalid gate, no jump on input edits; existing calculator/engine goldens; full suite before publication.
- No financial-value telemetry. No production/paid/remote data operations. Roll back only this UI/hook slice.

Astra implements and reviews directly under the current owner instruction, without Gemini. Keep a small reviewable source commit; one checkpoint full gate before push. Record source/preview/CI/actual evidence in the canonical C17 review and B52 submission. Native reader residuals and consolidated zoom schedule remain as recorded; do not claim WCAG conformance. Expected outcome is fewer manual scroll searches after calculation; measure with consented task completion, not invented user results.
