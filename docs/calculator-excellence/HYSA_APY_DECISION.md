# HYSA APY correction decision — 2026-09-29 (implemented and accepted in C15)

Decision owner: Astra; original source baseline `50d817d`. Implemented at `7192bdd13f8a7b4744df45ef296687e2abe62f9b`; [C15 acceptance](../execution/reviews/C15.md) records goldens, history behavior and hosted proof. Only `/calculators/hysa` is in scope. FIRE and other compound/SIP/401(k) nominal-rate conventions remain unchanged; CD's annual APY calculation already matches its label.

[CFPB APY reference](https://www.consumerfinance.gov/rules-policy/regulations/1030/a/) defines yield including compounding; [FDIC's explanation](https://www.fdic.gov/consumer-compliance-examination-manual/vi-3-truth-savings) confirms that interest and compounding frequency determine yield. For this constant-rate, monthly, end-of-period planning model, derive monthly growth as `m=(1+y)^(1/12)-1`, where `y=entered APY/100`. This is an equivalent-month planning approximation, not a claim to reproduce a bank's daily accrual, leap days, changing APY or interest-credit dates.

The pre-correction route was labeled APY but reused nominal `rate/12`. Independent recurrence: `balance=principal`; each month `balance=balance*(1+m)+monthlyDeposit`; after every twelfth month's deposit add the explicit annual top-up. Totals, schedule, chart, sensitivity, scenarios and exported summaries must all use this same basis and order. Do not just relabel the input nominal or alter a display number.

Goldens (absolute tolerance 0.01): $10,000, no deposits, 4.25% APY, 1 year → $10,425.00; $10,000 + $500/month, 4.25%, 3 years, no top-up → $30,468.781876553145 (old $30,519.033740012204); CD $10,000 at 4.5% APY for 2y → $10,920.25 unchanged. Zero APY gives principal plus contributions exactly. Cover zero balance, additional yearly top-up, fractional horizon under the existing documented event-count convention, and supported min/max rates. References establish APY meaning; these goldens are independent mathematical derivations.

Historical saved input `rate` was presented to users as APY, so retain that declared input meaning. Keep original saved metrics immutable as historical snapshots. A load/recalculation must visibly state the corrected APY method, show the delta from a historical result where present, and save a new result only on explicit user action. Inspect existing result/DTO version metadata first: use an additive calculation-method marker only if the existing parser/storage contract can preserve it; otherwise identify historical recalculation through supported created-at/method metadata and document the exact backward-compatible choice in the submission. No remote D1 migration or rewrite is authorized by this decision. Never silently overwrite prior outcomes. Public share links continue to carry APY as labeled; disclose that current computation uses the corrected basis.

Rollback: revert the isolated HYSA computation/display adapter together, with an honest temporary APY limitation or disabled erroneous projection; retain old and new historical records. Do not revert unrelated nominal calculations. Regression tests and exact-source hosted checks by Astra precede acceptance.

Implementation uses the existing persisted `result.assumptions` array and the stable string `APY includes compounding; this estimate converts it to an equivalent monthly rate.` as its backward-compatible method marker. Do not casually edit that string: historical-method recognition depends on it. Explicit loading of an unmarked snapshot shows the old estimate, current corrected estimate and difference; input edits clear that method-only comparison. Original snapshots stay immutable; saving the corrected calculation is an explicit action. No schema or hosted data migration occurred.
